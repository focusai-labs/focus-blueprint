# כניסה לפרויקט קיים

בכל מקום שכתוב `bp`, מריצים `node "${CLAUDE_PLUGIN_ROOT}/scripts/bp.mjs"`. הפירוט של כל צעד נמצא בתיקייה `${CLAUDE_PLUGIN_ROOT}/skills/adopt/references`.

בפרויקט קיים כבר יש קוד שעובד, ולפעמים גם משתמשים אמיתיים. לכן קודם מסתכלים בלי לשנות דבר ומסכמים עם הסטודנט מי רשאי לעשות מה. רק אחרי זה מתקנים, בקבצים חדשים שנבדקים לפני שהם מגיעים לפרודקשן.

## שתי דרכים להתחיל

1. כשהפרויקט כבר במחשב, הסטודנט פותח את Claude Code בתיקייה שלו. כשיש שינויים שלא נשמרו, הוא מחליט אם לעשות להם commit או להעביר אותם הצידה.
2. כשהפרויקט רק ב-GitHub, מורידים אותו עם `gh repo clone <owner>/<repo> <תיקייה>`. אחר כך הסטודנט פותח שיחה חדשה בתיקייה החדשה ומפעיל שוב את `/focus-blueprint:adopt`, כי החיבורים ב-`.mcp.json` והשומרים של הכלי פועלים לפי התיקייה שבה השיחה נפתחה.

בשתי הדרכים עובדים בענף חדש, עם `git switch -c adopt`.

## לפני הכל: החיבורים

כל חיבור נבדק בכלי שמדווח עליו הכי טוב, לפי `connections.md`. בודקים את `gh auth status`, את `supabase projects list`, את `supabase migration list --remote` ואת `claude mcp list`. כשהאתר עולה דרך Vercel, בודקים גם את `vercel whoami`. שרת של Supabase שבכתובת שלו אין `project_ref` רואה את כל הפרויקטים בחשבון. הסטודנט מכבה אותו בפרויקט הזה דרך `/mcp`, ו-Claude לא קורא לכלים שלו. ב-n8n ובכל שרת אחר שהפרויקט משתמש בו עושים קריאה אחת לקריאה בלבד דרך השרת עצמו. חיבור שחסר הסטודנט מחבר בעצמו, ובלי חיבור שהפרויקט צריך לא ממשיכים.

## הסדר

### 1. סקירה בקריאה בלבד

לא משנים שום קובץ, הגדרה או נתון. קוראים את הקוד, את המסד, את האוטומציות ואת ההגדרות של הפרויקט עצמו, `CLAUDE.md`, ה-hooks וה-skills, לפי `review.md`. הממצאים נכתבים ב-`spec/adopt-review.md`. לכל דבר בהגדרות שמתנגש בתהליך של הכלי, מיושן או כפול, כותבים ב-`spec/adopt-setup.md` הצעה עם diff והסבר. קובץ קיים לא דורסים.

כאן עוצרים בפעם הראשונה. מסבירים לסטודנט בעברית פשוטה מה נמצא, מה מסוכן ומה מציעים. הוא מאשר, מתקן או עוצר, ומותר לו לאשר רק חלק מההצעות.

### 2. הכלי, המפה ומטריצת ההרשאות

1. מריצים `bp init --name "<שם הפרויקט>"`. הפקודה מתקינה גם את ה-hook של git, ולכן מכאן commit עובר רק כשהבדיקה עוברת.
2. כשיש במערכת משתמשים אמיתיים, מריצים מיד `bp state set live=true`, כדי שהשומרים יחסמו דחיפה ישירה לפרודקשן.
3. מחילים רק את ההצעות שהסטודנט אישר, ומראים לו את `git diff` של כל קובץ.
4. מסדרים את המיגרציות לפי `migrations.md`. תיקייה ישנה, `db/migrations`, מעבירים ל-`supabase/migrations` רק אחרי שבודקים את ההיסטוריה עם `supabase migration list --remote`. אחר כך בונים את המפה ואת המטריצה לפי `map-and-matrix.md`. ברירת המחדל במטריצה היא שהכל חסום, ועל תא שלא ברור שואלים.

כאן עוצרים בפעם השנייה. עוברים עם הסטודנט על המטריצה תא אחרי תא. כל תיקון שלו נרשם עם `bp access set`, ואחריו מריצים שוב את `bp render`.

### 3. תיקונים במיגרציות חדשות

כל תיקון במסד הוא קובץ חדש מ-`supabase migration new <name>`, בתיקייה `supabase/migrations`. מיגרציה שכבר רצה לא עורכים. כל קובץ נבדק קודם על מסד בלי משתמשים אמיתיים, ומגיע לפרודקשן רק כשה-PR מתמזג. סוד שנמצא בקוד או ב-Git עובר למשתנה סביבה בשרת, והסטודנט מחליף את המפתח אצל הספק. אחרי כל קובץ מריצים `node scripts/blueprint-check.mjs`.

### 4. בדיקות

מוכיחים כמשתמש שני שהוא לא רואה ולא משנה את השורות של הראשון, ושומרים את הפלט של ה-advisors כהוכחה, בקובץ שמתחיל בשורה כמו `# supabase advisors 2026-11-25`. אחר כך ממלאים את קובצי הבדיקה של היכולות שהתיקונים נגעו בהן.

### 5. המסמכים לפי התבניות

כותבים את `spec/idea.md`, `spec/prd.md`, `spec/builder-check.md` ו-`db/schema.md`, ומעבירים מסמכים קיימים לתבניות של הכלי, לפי `documents.md`. בכל מסמך קיים מראים לסטודנט את ההבדלים לפני שמחליפים. אחר כך מריצים `bp state set stage=12`.

### 6. אכיפה

מריצים `bp githook install`, בודקים שהקובץ `.github/workflows/blueprint-check.yml` קיים, ומגדירים כמו בשלב 1 את ההגנה על `main` ואת חיבור ה-MCP של Supabase לפרויקט אחד ולקריאה בלבד. בסוף מריצים את ההוכחה שהשערים עובדים, לפי `${CLAUDE_PLUGIN_ROOT}/skills/stage-11-skeleton/references/gate-proof.md`, ושומרים אותה ב-`docs/evidence/gates.txt`.

## מתי עוצרים

מלבד שתי העצירות שלמעלה, עוצרים ושואלים רק בארבעה מקרים: לפני פעולה שמוחקת נתונים, לפני שינוי בהרשאות או במפתחות, לפני פעולה שעולה כסף או מעלה משהו לאוויר וכשאי אפשר להמשיך בלי לנחש. כל הכרעה אחרת רושמים עם `bp ruling add`.

## מה חייב להיות נכון בסוף

- הבדיקה `node scripts/blueprint-check.mjs` עוברת בשלב 12. אזהרות על יכולות שקיימות מלפני הכלי הן צפויות.
- בקובץ `spec/adopt-review.md` יש את המטריצה שהסטודנט אישר, והקובץ `spec/ux-review.md` קיים כקו בסיס.
- הפקודה `supabase migration list --remote` מראה כל גרסה גם בקבצים וגם במסד.
- בקובץ `docs/evidence/gates.txt` כל שער עבר, או שכתוב לידו למה הוא לא רלוונטי.

## סגירה

עושים commit בענף `adopt`, פותחים PR וממזגים אחרי שהבדיקה עוברת. כותבים את `.blueprint/last-session.md`, ואומרים לסטודנט בשלוש שורות מה נמצא, מה תוקן ומה הצעד הבא, שמתחיל ב-`/blueprint`.
