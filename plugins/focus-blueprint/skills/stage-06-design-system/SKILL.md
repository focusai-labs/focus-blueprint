# שלב 06: כיוון עיצובי

בכל מקום שכתוב `bp`, מריצים `node "${CLAUDE_PLUGIN_ROOT}/scripts/bp.mjs"`.

## למה השלב הזה קיים

ויכוח על "יפה" לא נגמר, ובחירה מתוך דוגמאות חיות נגמרת בדקה. מהבחירה יוצאות שלוש גרסאות של המסך המרכזי, ורק אחרי שהסטודנט בוחר אחת נכתבת מערכת העיצוב. מערכת עיצוב היא כללים ולא רק צבעים: ניגודיות שאפשר לקרוא, צבע שלא נושא משמעות לבד, ופעולה ראשית אחת בכל מסך.

## מה קוראים לפני שמתחילים

- בקובץ המצב `.blueprint/state.json`, השלב הנוכחי הוא 6. אם לא, מפנים ל-`/blueprint`.
- המסמכים `spec/users.md`, `spec/screens-map.md`, והמפה `.blueprint/map.json`.
- הקטלוג בתיקייה `${CLAUDE_PLUGIN_ROOT}/data/catalog`.
- בעקרונות `${CLAUDE_PLUGIN_ROOT}/data/ux/principles.json`, כל מה שמסומן לשלב 6, ובמיוחד D4, D6, D7, D8, D24, D28, D33 ו-D34.

## מה עושים

1. מריצים `bp stage start 6`.
2. שואלים אם יש לוגו, צבעים, גופנים או תמונות של המותג, ומבקשים לשים אותם בתיקייה `design/assets`.
3. פותחים את הקטלוג: `node "${CLAUDE_PLUGIN_ROOT}/ui/serve.mjs" --page catalog`, ומחכים עם `node "${CLAUDE_PLUGIN_ROOT}/ui/wait.mjs" --name round-b --until done --timeout 280`. אחר כך עוברים על שאר שאלות הסבב השני באותו דף: `--page questionnaire --round b`.
4. בונים שלוש גרסאות של המסך המרכזי, בקבצים `mockup/_direction-1.html`, `mockup/_direction-2.html` ו-`mockup/_direction-3.html`. כל גרסה שונה באמת מהאחרות, וכולן משתמשות בתוכן האמיתי של המסך מתוך מפת המסכים.
5. מראים את שלוש הגרסאות, בדפדפן או בצילומי מסך, בשני רוחבים: מחשב וטלפון. הסטודנט בוחר אחת, ואפשר לבקש שינוי קטן לפני הבחירה. רושמים: `bp log add kind=wording text="<הגרסה שנבחרה ולמה>" decision=now stage=6`.
6. כותבים את `design/design-system.md`:
   - הטוקנים: צבעים, גופנים, מרווחים, פינות וצללים.
   - כללי השימוש, כל אחד במשפט שאפשר לבדוק: ניגודיות של לפחות 4.5 ל-1 לטקסט רגיל ו-3 ל-1 לטקסט גדול, לפי WCAG 2.2 סעיף 1.4.3. צבע אף פעם לא לבד. טקסט על תמונה מקבל שכבה כהה או צל. לטקסט רץ יש רוחב מרבי. בכל מסך יש פעולה ראשית אחת. מימין לשמאל, כולל סדר הצעדים וכיוון האייקונים.
   - מצב יום כברירת מחדל, עם מתג למצב לילה, אלא אם הסטודנט בחר אחרת בסבב השני.
7. כותבים את הטוקנים גם לקובץ `design/tokens.css`. הגרסה שנבחרה עוברת להשתמש בו.
8. אורזים את מערכת העיצוב גם כ-skill: `design/skill/SKILL.md`, עם תיאור קצר ועם ההפניה לשני הקבצים, כדי שאפשר יהיה לקחת אותה לפרויקט אחר.

## מה חייב להיות נכון בסוף (ההוכחה)

- שלושת קובצי הגרסאות קיימים.
- הבחירה רשומה ביומן השינויים `.blueprint/changes.json`.
- הגרסה שנבחרה טוענת את `design/tokens.css`, ואין בה צבעים שלא באים מהטוקנים.
- הקובץ `design/design-system.md` מכיל את כל כללי השימוש מצעד 6.

## מה נשאר בתיקייה

- הקבצים `design/design-system.md`, `design/tokens.css` ו-`design/skill/SKILL.md`
- שלוש הגרסאות בתיקייה `mockup`
- נכסי המותג בתיקייה `design/assets`

## סגירה

1. מריצים את בדיקות ההוכחה, ושומרים את הפלט האמיתי.
2. מציגים את ההכרעות של השלב: `bp ruling list --unreported --stage 6`, ואז `bp ruling report --stage 6`.
3. סוגרים: `bp stage done 6 --status <done|done_with_concerns|blocked|needs_context> --note "<מה פתוח>" --proof "<הפלט>"`. כשעיקרון ברמה `should` נדחה לרשימת "אחר כך", הסטטוס הכן הוא `done_with_concerns`, והוא כתוב בהערה.
4. עושים commit בענף `stage-06` עם הודעה בעברית, PR, ומיזוג אחרי שהבדיקה עוברת.
5. כותבים את `.blueprint/last-session.md`.
6. אומרים לסטודנט בשורה אחת כנה איך השלב נסגר. אחר כך שתי שורות: הבא בתור הוא ה-mockup, בשיחה חדשה עם `/blueprint`.
