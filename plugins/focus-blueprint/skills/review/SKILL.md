# סקירה עצמאית

בכל מקום שכתוב `bp`, מריצים `node "${CLAUDE_PLUGIN_ROOT}/scripts/bp.mjs"`.

מי שבנה לא בודק את עצמו. הסוקר הוא סוכן חדש, בלי השיחה, שמקבל רק את מה שצריך כדי לשפוט.

## לפני הסקירה

- יש תקציר ב-`evals/briefs/<id>.md`, ראיה ירוקה ב-`evals/evidence/<id>.green.txt`, וענף `cap-<id>`.
- מריצים `bp route review`. מה שהפקודה מחזירה קובע איך הסקירה רצה, אבל התוצאה תמיד נכתבת לאותו קובץ ונרשמת באותה פקודה.

## הסקירה

1. מתעדים את `git status` לפני.
2. שולחים את הסוכן `focus-blueprint:capability-reviewer`. אם אי אפשר לשלוח אותו בשם הזה, שולחים `general-purpose` עם ההנחיה מהקובץ `${CLAUDE_PLUGIN_ROOT}/agents/capability-reviewer.md`. הוא מקבל רק נתיבים: התקציר, קובץ הבדיקה, הראיה הירוקה, תיקיית `spec`, מסך היכולת ב-`mockup`, ואת טווח השינויים `main...cap-<id>`.
3. אחרי שהוא חוזר, בודקים ש-`git status` לא השתנה. אם השתנה, מבטלים את מה שהסוקר שינה, ומדווחים.
4. כותבים את התשובה שלו, כמו שהיא, לקובץ `evals/reviews/<id>.md`.

## כשהממצאים חוזרים

1. בודקים כל ממצא לפני שנוגעים בקוד: קוראים את השורה, מריצים, ומבינים. לא מסכימים אוטומטית.
2. ממצא נכון מתקנים, ומוסיפים בדיקה שתופסת אותו.
3. ממצא שגוי לא מתקנים, וכותבים בקובץ הסקירה, מתחת לממצא, את הנימוק במשפט אחד.
4. כל סבב שנשאר בו ממצא פתוח נרשם: `bp round add capability <id> --note "<הממצא>"`. כשהפלט הוא `stop: true`, עוצרים ומביאים לסטודנט את מה שפתוח.
5. אחרי התיקונים, שולחים שוב את הסוקר, עד ששני פסקי הדין הם "עבר".

## הרישום

מריצים `bp review record <id> --spec pass --quality pass --path evals/reviews/<id>.md`. הכלי מסרב בלי ראיה ירוקה, ובלי שני פסקי דין של "עבר".
