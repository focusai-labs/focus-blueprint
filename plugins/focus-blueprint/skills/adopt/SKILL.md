# כניסה לפרויקט קיים

בכל מקום שכתוב `bp`, מריצים `node "${CLAUDE_PLUGIN_ROOT}/scripts/bp.mjs"`.

לא חייבים להתחיל לעבוד עם הכלי מהרעיון. בפרויקט שכבר רץ, הכלי בונה את המפה ממה שקיים, כדי שכל שינוי מעכשיו יעבור דרך המסמכים, הבדיקות וכללי ה-Git.

## הסדר

1. מריצים `bp init --name "<שם הפרויקט>"`. הפקודה לא דורסת קבצים קיימים, ומוסיפה את כללי העבודה ל-`AGENTS.md`.
2. סורקים במאגר את הדפים או הנתיבים, את קובצי המיגרציה ואת העותקים של ה-workflows. כשאין קובצי מיגרציה, מושכים את הסכמה דרך ה-MCP של Supabase וכותבים אותה כקובץ מיגרציה ראשון, בלי להריץ אותו שוב.
3. מריצים על האתר החי את סריקת המלאי, `${CLAUDE_PLUGIN_ROOT}/scripts/inventory.browser.js`, ואת `/focus-blueprint:ux-review`. הסקירה הזאת היא קו הבסיס, והיא נשמרת ב-`spec/ux-review.md`.
4. בונים את המפה ממה שנמצא, כלומר מסכים, טבלאות, אוטומציות ויכולות, עם `bp map add`.
5. כל יכולת שכבר עובדת מסמנים כקיימת מלפני הכלי, עם `bp map set capability <id> status=real --baseline`. הסימון אומר במפורש שהיא לא נבנתה דרך התהליך, ובדיקת המפה מזכירה את זה באזהרה.
6. מעבירים את הפרויקט לשלב 12 עם `bp state set stage=12`. כשכבר יש משתמשים אמיתיים, מריצים גם `bp state set live=true`, ומהרגע הזה מיגרציה רק מוסיפה דברים לסכמה.
7. מסבירים לסטודנט בשלוש שורות מה נמצא, מה חסר ומה הצעד הבא. בדרך כלל הצעד הבא הוא לכתוב בדיקות קבלה ליכולות הקיימות, או השינוי שבשבילו הוא הכניס את הכלי.

## מה חייב להיות נכון בסוף

- הבדיקה `node scripts/blueprint-check.mjs` עוברת על המפה החדשה. אזהרות על יכולות שקיימות מלפני הכלי הן צפויות.
- הקובץ `spec/ux-review.md` קיים, כקו בסיס.
