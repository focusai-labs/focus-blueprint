# אב הטיפוס: בנייה, סקירה ושיתוף

מסך בודד מראה איך המסך נראה. באב טיפוס שכל הכפתורים בו עובדים אפשר לבדוק אם עוברים את כל התהליך, מההתחלה ועד הסוף. מפת הדפים מראה בכל רגע מה כבר נבנה ומה עוד חסר, ולכן ברור לכולם מה עוד לא קיים.

בכל מקום שכתוב `bp`, מריצים `node "${CLAUDE_PLUGIN_ROOT}/scripts/bp.mjs"`.

## בנייה ובדיקת הכפתורים

1. מריצים `bp prototype build`. הפקודה כותבת קובץ אחד, `mockup/prototype.html`, ובו כל המסכים הבנויים, מפת דפים שנבנית מהמפה, מעבר בין תצוגת טלפון לתצוגת מחשב ופס שאומר שזה אב טיפוס עם נתוני דמה. מסך שרשום במפה ועוד לא נבנה מופיע במפת הדפים עם סימון, ואף פעם לא כמסך גמור.
2. כשהפקודה מדווחת שהקובץ גדול מדי, מקטינים את התמונות הגדולות שהיא מציינת ובונים שוב.
3. קוראים עם הכלי Read את הקובץ `${CLAUDE_PLUGIN_ROOT}/scripts/prototype-check.browser.js`. בכלי ה-MCP של Playwright מריצים `browser_navigate` לכתובת של `mockup/prototype.html`, ואחר כך `browser_evaluate` עם הטקסט של הקובץ בשדה `function`.
4. כל כפתור או קישור שהבדיקה מחזירה ב-`dead` או ב-`nothing` מחברים למסך שלו, או מסמנים `data-demo` כשבאב הטיפוס הוא לא אמור לעשות כלום. בונים ובודקים שוב, עד ששתי הרשימות ריקות.
5. כשאין Playwright MCP, או שהדפדפן תפוס, אומרים את זה במפורש, והבדיקה לא נחשבת כאילו עברה.

## סקירת המסכים עם הסטודנט

1. פותחים את הסקירה עם `node "${CLAUDE_PLUGIN_ROOT}/ui/serve.mjs" --page prototype`, ומחכים עם `node "${CLAUDE_PLUGIN_ROOT}/ui/wait.mjs" --name prototype --until done --timeout 280`. כשהזמן נגמר לפני שהסטודנט סיים, מריצים את אותה פקודת המתנה שוב.
2. אומרים לסטודנט בשורה אחת לעבור על אב הטיפוס כמו משתמש, ולהשאיר לכל מסך הערה או אישור.
3. קוראים את התשובות מהקובץ `.blueprint/ui/answers/prototype.json`. מתקנים כל מסך שיש עליו הערה, ובונים ובודקים שוב כמו בחלק הקודם.
4. פותחים את הסקירה מחדש. מהסבב השני הגרסה הקודמת מוצגת ליד החדשה, וההערה מהסבב הקודם מופיעה ליד המסך, כדי שהסטודנט יראה מה השתנה.
5. ממשיכים עד שכל המסכים הבנויים מאושרים. הערה שמשנה את האפיון מטפלים בה כמו בתשובה מהסבב השלישי: היא נכנסת ל-PRD עם סימון המקור שלה ולמסמך ההחלטות, ומה שנוגע במפה משנים רק דרך `bp`.

## שיתוף, רק באישור של הסטודנט

1. מריצים `bp prototype scan`. סוד שנמצא מוחקים מהמסכים ובונים שוב. את רשימת הפרטים האישיים מראים לסטודנט, והוא מאשר במשפט שלו שכל הנתונים מומצאים. פרט שהוא לא בטוח לגביו מחליפים בנתון דמה.
2. לפני הפרסום הראשון בודקים בתיעוד הרשמי, דרך `/focus-blueprint:docs-verify` עם הנושא `claude-artifacts` והקישור `https://code.claude.com/docs/en/artifacts`, אם אפשר לפרסם artifact מהסשן הזה ובאילו תנאים.
3. שואלים את הסטודנט אם לפרסם את אב הטיפוס כ-artifact, ואומרים לו בשתי שורות, לפי הסיכום מהתיעוד, איפה הוא נשמר, מי יכול לראות אותו כשהוא נוצר ועם מי אפשר לשתף אותו. מפרסמים רק אחרי "כן" מפורש, כי Claude Code יכול לפרסם artifact גם בלי לשאול.
4. אחרי הפרסום רושמים את הקישור עם `bp state set where.prototypeUrl=<url>`. כל עדכון אחר כך מפרסמים לאותה כתובת, כדי שמי שכבר קיבל את הקישור יראה את הגרסה החדשה ולא יקבל קישור חדש.
5. כשאי אפשר לפרסם artifact, או שהסטודנט לא רוצה, אומרים את זה במשפט אחד ומציעים שתי דרכים אחרות. אפשר לשלוח את הקובץ עצמו, שנפתח בכל דפדפן גם בלי רשת. אפשר גם להעלות את התיקייה `mockup` ל-Vercel לפי השלב של ה-mockup במסלול, בקבצים שבתיקייה `${CLAUDE_PLUGIN_ROOT}/data/tracks`. כשבמסלול אין צעד כזה, מעלים HTML פשוט עם קובץ אחד של נתוני דמה, כפרויקט ב-Vercel שמחובר ל-repo. בשתי הדרכים אין שום סוד בקבצים. לפני הפקודה קוראים את התיעוד דרך `/focus-blueprint:docs-verify`, ורושמים את הקישור עם `bp state set where.mockupUrl=<url>`.
6. רושמים איך הסטודנט בחר לשתף ולמה, עם `bp log add kind=wording text="<הדרך שנבחרה והסיבה>" decision=now stage=7`.

## גרסה לבדיקה עם אדם אמיתי

בבדיקת שמישות מי שנבדק צריך למצוא את הדרך בעצמו, ולכן מפת הדפים לא מופיעה בה. הפקודה `bp prototype build --test` כותבת את `mockup/prototype-test.html`, בלי מפת הדפים ובלי המעבר בין הגדלים. את הגרסה הזו משתפים באותן דרכים ובאותם כללים.
