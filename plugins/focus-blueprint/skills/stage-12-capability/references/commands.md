# הפקודות של שלב 12, צעד אחרי צעד

בכל מקום שכתוב `bp`, מריצים `node "${CLAUDE_PLUGIN_ROOT}/scripts/bp.mjs"`.

## לפני היכולת הראשונה

- כל תרחיש של תהליך נכתב בקובץ `evals/cases/<process>-<case>.md`, בשלוש שורות: המצב בהתחלה (בהינתן, Given), מה קורה (כש, When) ומה רואים בסוף (אז, Then). מקשרים אותו עם `bp process case set <process> <case> --json '{"eval":"evals/cases/<process>-<case>.md"}'`.
- שעון מקבל בדיקה באותה צורה, עם `bp process timer set <process> <timer> --json '{"test":"evals/cases/<process>-<timer>.md"}'`.
- אחרי שכל התרחישים והשעונים מקושרים מריצים `bp render`. בלי זה בדיקת המפה נכשלת, כי בטבלאות של התרחישים והשעונים ב-PRD יש עמודה של הבדיקה.
- אבן הדרך של כל יכולת נרשמת עם `bp map set capability <id> milestone=<n>`. המספר מגיע מטבלת אבני הדרך במסמך שלפני הבנייה, `docs/pre-build.md`.

## התקציר

- הפקודה `bp brief <id>` יוצרת את `evals/briefs/<id>.md` מהמפה, עם המסכים, הטבלאות, ההרשאות, האוטומציות ונתיב הבדיקה.
- בטבלת הערכים, בכל שורה יש ערך מדויק ואת הקובץ שממנו הוא נלקח, למשל `| העלאה הושלמה | mockup/upload.html |`. בדיקת המפה מוודאת שהקובץ הזה קיים.
- בחלק האחרון של התקציר, "מה הבונה לא צריך להחליט", כותבים כל בחירה שהבנייה יכולה להעלות, ולצידה את ההחלטה ואת המקום שבו היא רשומה. כל עוד נשאר שם `<<fill>>`, בדיקת המפה נכשלת על היכולת ברגע שהיא מסומנת כאמיתית.

## הבדיקה והראיות

- הפקודה `bp eval new <id>` יוצרת את `evals/<id>.md`, עם מקום למשפט שאומר מה הבדיקה תופסת ולחמשת מצבי הכשל.
- כשהבדיקה רצה בדפדפן דרך ה-MCP של Playwright ולא כסקריפט, שומרים את הדוח בקובץ ומריצים `bp evidence red <id> --report <file> --result fail`. אחר כך מריצים את אותה פקודה עם `green` ו-`pass`.
- הכלי לא רושם ראיה אדומה כשהבדיקה עברה, וגם לא ראיה ירוקה כשלא נרשמה לפניה ראיה אדומה. כשהבדיקה לא רצה בכלל, למשל כי הפקודה לא נמצאה, שום ראיה לא נרשמת.

## הצעדים בתהליך

- אחרי שהבדיקה עוברת, כל צעד שהיכולת מממשת מקבל את מה שנבנה: `bp process step set <process> <step> --json '{"capability":"<id>","tables":["<table>"],"permission":"<role>:<op>:<table>:<scope>","test":"evals/<id>.md"}'`. ההרשאה כתובה באותה צורה כמו ברשימת ההרשאות של היכולת במפה.
- אחרי העדכון מריצים `bp render`, כדי שהחותמת של ה-PRD תתאים למפה.

## הסקירה

- הסקירה נכתבת לקובץ `evals/reviews/<id>.md`, עם שני פסקי דין, עמידה באפיון ואיכות. ליד כל ממצא כתובים הקובץ והשורה.
- רק כששני פסקי הדין הם "עבר", מריצים `bp review record <id> --spec pass --quality pass --path evals/reviews/<id>.md`.
- כשהסוקר לא סיים, מריצים `bp review record <id> --spec not_run --quality not_run --path evals/reviews/<id>.md` ושולחים אותו שוב. כל עוד זה הרישום האחרון, הכלי לא מסמן את היכולת כאמיתית.

## אבן דרך שהושלמה

- כשכל היכולות שמסומנות באותו `milestone` אמיתיות, כותבים את `docs/milestone-<n>.md` מהתבנית `${CLAUDE_PLUGIN_ROOT}/templates/docs/milestone-<client|org|self>.md`. התבנית נבחרת לפי ההקשר: `client` כשמי שמשלם הוא לקוח, `org` כשזה הארגון ו-`self` כשבונים לעצמכם.

## בקשת מיזוג (PR) ומיזוג

- לכל יכולת יש PR משלו. ב-PR רצות הבדיקות: ה-build, בדיקות הקבלה ובדיקת המפה.
- במאגר פרטי, GitHub חוסם מיזוג של PR עם בדיקה אדומה רק בתוכנית בתשלום, וההגנה על main הוגדרה כבר בשלב 1. כשנשארים בחשבון החינמי, ה-hook של git מריץ את הבדיקה לפני כל commit, ו-Claude לא ממזג PR עם בדיקה אדומה.

## כשמשהו שבור כבר עלה לאוויר

- ב-Vercel אפשר לחזור מיד לגרסה קודמת. פרויקט של לקוח רץ על Pro, ושם אפשר לחזור לכל גרסה. בתוכנית החינמית אפשר לחזור רק לגרסה שלפני האחרונה.
- אחרי שחוזרים לגרסה קודמת, Vercel מפסיקה להעלות לאוויר את מה שנכנס ל-main, עד שמבטלים את החזרה. המקור הוא https://vercel.com/docs/instant-rollback
- את התיקון עושים בענף, דרך PR ובדיקה ירוקה, ורק אחר כך מבטלים את החזרה.
