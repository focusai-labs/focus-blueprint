# כניסה לפרויקט קיים

בכל מקום שכתוב `bp`, מריצים `node "${CLAUDE_PLUGIN_ROOT}/scripts/bp.mjs"`.

הכלי לא חייב להתחיל מהרעיון. בפרויקט שכבר רץ, הוא בונה את המפה ממה שקיים, כדי שכל שינוי מכאן והלאה יעבור דרך המסמכים, הבדיקות וכללי Git.

## הסדר

1. מריצים `bp init --name "<שם הפרויקט>"`. הפקודה לא דורסת קבצים קיימים, ומוסיפה את כללי העבודה ל-`AGENTS.md`.
2. סורקים את המאגר: הדפים או הנתיבים, קובצי המיגרציה, והעותקים של ה-workflows. כשאין קובצי מיגרציה, מושכים את הסכמה דרך ה-MCP של Supabase, וכותבים אותה כקובץ מיגרציה ראשון, בלי להריץ אותו שוב.
3. מריצים על האתר החי את סריקת המלאי, `${CLAUDE_PLUGIN_ROOT}/scripts/inventory.browser.js`, ואת `/focus-blueprint:ux-review`. הסקירה הזאת היא קו הבסיס, ונשמרת ב-`spec/ux-review.md`.
4. בונים את המפה ממה שנמצא: מסכים, טבלאות, אוטומציות ויכולות, עם `bp map add`.
5. מסמנים כל יכולת שכבר עובדת כקיימת מלפני הכלי: `bp map set capability <id> status=real --baseline`. הסימון אומר בגלוי שהיא לא נבנתה דרך התהליך, ובדיקת המפה מזכירה את זה.
6. מעבירים את המצב לשלב 12: `bp state set stage=12`. כשיש משתמשים אמיתיים, גם `bp state set live=true`, ומאז כל מיגרציה מוסיפה בלבד.
7. מסבירים לסטודנט בשלוש שורות מה נמצא, מה חסר, ומה הצעד הבא. בדרך כלל זה בדיקות קבלה ליכולות הקיימות, או השינוי שבגללו הוא בא.

## מה חייב להיות נכון בסוף

- הבדיקה `node scripts/blueprint-check.mjs` עוברת על המפה החדשה. האזהרות על יכולות שקיימות מלפני הכלי צפויות.
- הקובץ `spec/ux-review.md` קיים, כקו בסיס.
