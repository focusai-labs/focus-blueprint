# שלב 04: מסמך PRD ובחירת מסלול

בכל מקום שכתוב `bp`, מריצים `node "${CLAUDE_PLUGIN_ROOT}/scripts/bp.mjs"`.

## למה השלב הזה קיים

מי שיבנה את המערכת הוא סוכן, והוא ממלא כל חוסר בניחוש. לכן ה-PRD כתוב במשפטים שאפשר לבדוק: לכל יכולת יש משפט שאומר איך נדע שהיא עובדת, לכל החלטה יש נימוק, ומה שבחוץ כתוב במפורש. המסלול והשירותים נבחרים בגלוי, מכרטיסים עם מחיר ועם המלצה, ולא נגזרים בשקט.

## מה קוראים לפני שמתחילים

- בקובץ המצב `.blueprint/state.json`, השלב הנוכחי הוא 4. אם לא, מפנים ל-`/blueprint`.
- `spec/idea.md`, `spec/decisions.md`, `spec/users.md`.
- התבנית `${CLAUDE_PLUGIN_ROOT}/templates/docs/prd.md`.
- הצמתים בתיקייה `${CLAUDE_PLUGIN_ROOT}/data/junctions`: הקובץ `track.json`, וכל קובץ שבשדה `opens_at` שלו יש 4.

## מה עושים

1. `bp stage start 4`.
2. **המסלול, כגישות.** מריצים `bp junction eligible track`. מציגים את שתיים או שלוש הגישות שנשארו, כל אחת בכרטיס: מתי היא מתאימה, מתי פחות, מה צריך להחזיק בחשבונות כל חודש, מה המחיר של הבחירה, וההמלצה עם הנימוק. עלויות ומגבלות נקראות מהתיעוד הרשמי דרך `/focus-blueprint:docs-verify`, עם התאריך שבו נבדקו, ולא מהזיכרון. הסטודנט בוחר, ואז `bp state set track=<id>` ו-`bp log add kind=track text="<הבחירה והנימוק>" decision=now stage=4`. אף פעם לא קובעים מסלול בלי הכרטיס.
3. **שאר הצמתים.** כל צומת שנפתח בשלב 4 מוצג באותה צורה. הבחירה נרשמת ב-`bp log add` וב-`bp state set`.
4. **המסמך.** ממלאים את `spec/prd.md` מהתבנית, בכל החלקים שלה:
   - הכוונה ולמה, מתוך התשובה הראשונה של הסטודנט.
   - המטרות, ומה לא מטרה.
   - **אנטי מטרות** (`<!-- prd:anti-goals -->`): מה ייחשב כישלון גם אם הכל עובד. Claude מציע שתי אפשרויות, והסטודנט בוחר או כותב מחדש. משפט אחד או שניים.
   - היכולות. לכל יכולת משפט אחד שאומר איך נדע שהיא עובדת, מנוסח כמו קריטריון קבלה: מי, עושה מה, באיזה תנאי, ומה רואים בסוף.
   - **מטריצת הרשאות**: תפקידים בשורות, סוגי מידע בעמודות, ובכל תא ליצור, לקרוא, לעדכן או למחוק, ואם רק את שלו או את של כולם. אין תא ריק: מה שאסור כתוב "אסור".
   - **מטריצת אוטונומיה**, כשיש אוטומציות: לכל אוטומציה מה מפעיל אותה, באיזו רמה היא רצה, מי מאשר, ומה קורה כשהיא נכשלת. מה שאפשר לכתוב ככלל בקוד לא נמסר למודל.
   - אילוצים, מגבלות של התוכניות שנבחרו, ושורת עלות חודשית.
   - הגישות שנשקלו, וההחלטות עם הנימוק שלהן.
   - מה נשאר לבונה להחליט.
   - רשימת "אחר כך": כל מה שנדחה נרשם גם ב-`bp map later add "<מה>" --stage 4`.
5. **שש העדשות.** עוברים על המסמך ושואלים שש שאלות:
   - האם יש דרישה שאי אפשר לבדוק?
   - האם יש פעולה שיוצאת לעולם בלי אישור?
   - האם יש נתון שלא ברור איפה הוא נשמר ומי קורא אותו?
   - האם יש תוכן שלא ברור מי שולט בו?
   - האם יש תקלה שלא הוגדר מה קורה בה?
   - האם יש החלטה שניתנה למודל, כשאפשר היה לכתוב אותה ככלל בקוד?
   כל ממצא נסגר באחת משתי דרכים: Claude מתקן ורושם הכרעה (`bp ruling add ... stage=4`), או שהשאלה עוברת לסטודנט. כותבים את הממצאים בסוף המסמך, תחת `<!-- prd:lenses -->`.
6. מראים לסטודנט את המסמך, ומתקנים עד שהוא מאשר מה בפנים ומה נדחה.

## מה חייב להיות נכון בסוף (ההוכחה)

- הבדיקה `node scripts/blueprint-check.mjs` לא מחזירה אזהרה על אנטי מטרות.
- לכל יכולת ב-`spec/prd.md` יש משפט הוכחה, ובמטריצת ההרשאות אין תא ריק.
- הפקודה `bp state get track` מחזירה מסלול, וב-`.blueprint/changes.json` יש רשומה מסוג `track`.
- לכל צומת שנפתח יש החלטה רשומה.
- ב-`.blueprint/map.json`, ברשימה `later`, נמצא כל מה שנדחה.

## מה נשאר בתיקייה

- `spec/prd.md`
- יומן השינויים `.blueprint/changes.json`, עם הבחירות

## סגירה

1. מריצים את בדיקות ההוכחה, ושומרים את הפלט האמיתי.
2. מציגים את ההכרעות של השלב: `bp ruling list --unreported --stage 4`, ואז `bp ruling report --stage 4`.
3. סוגרים: `bp stage done 4 --status <done|done_with_concerns|blocked|needs_context> --note "<מה פתוח>" --proof "<הפלט>"`.
4. עושים commit בענף `stage-04` עם הודעה בעברית, PR, ומיזוג אחרי שהבדיקה עוברת.
5. כותבים את `.blueprint/last-session.md`.
6. אומרים לסטודנט בשורה אחת כנה איך השלב נסגר. אחר כך שתי שורות: הבא בתור הוא מפת המסכים, בשיחה חדשה עם `/blueprint`.
