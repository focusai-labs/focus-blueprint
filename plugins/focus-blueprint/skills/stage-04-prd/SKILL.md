# שלב 04: מסמך PRD ובחירת מסלול

בכל מקום שכתוב `bp`, מריצים `node "${CLAUDE_PLUGIN_ROOT}/scripts/bp.mjs"`.

## למה השלב הזה קיים

את המערכת יבנה סוכן, וכל מה שחסר במסמך הוא ישלים בניחוש. לכן כותבים את ה-PRD במשפטים שאפשר לבדוק. לכל יכולת יש משפט שאומר איך נדע שהיא עובדת, לכל החלטה יש נימוק, ומה שלא נכנס כתוב במפורש. את המסלול ואת השירותים הסטודנט בוחר מתוך כרטיסים עם מחיר ועם המלצה, ו-Claude לא מחליט עליהם בלי לשאול.

## מה קוראים לפני שמתחילים

- בקובץ המצב `.blueprint/state.json` בודקים שהשלב הנוכחי הוא 4. אם לא, מפנים את הסטודנט ל-`/blueprint`.
- `spec/idea.md`, `spec/decisions.md`, `spec/users.md`.
- התבנית `${CLAUDE_PLUGIN_ROOT}/templates/docs/prd.md`.
- נקודות ההחלטה בתיקייה `${CLAUDE_PLUGIN_ROOT}/data/junctions`: הקובץ `track.json` וכל קובץ שבשדה `opens_at` שלו מופיע 4.

## מה עושים

1. מריצים `bp stage start 4`.
2. בוחרים מסלול מתוך גישות. מריצים `bp junction eligible track`, ומציגים את שתיים או שלוש הגישות שנשארו, כל אחת בכרטיס: מתי היא מתאימה ומתי פחות, אילו חשבונות צריך להחזיק כל חודש, מה המחיר של הבחירה ומה ההמלצה ולמה. את העלויות ואת המגבלות קוראים בתיעוד הרשמי דרך `/focus-blueprint:docs-verify`, וכותבים מתי נבדקו. לא מסתמכים על הזיכרון. אחרי שהסטודנט בוחר, מריצים `bp state set track=<id>` ו-`bp log add kind=track text="<הבחירה והנימוק>" decision=now stage=4`. אף פעם לא קובעים מסלול בלי להראות את הכרטיסים.
3. כל נקודת החלטה אחרת שנפתחת בשלב 4 מציגים באותה צורה, ורושמים את הבחירה ב-`bp log add` וב-`bp state set`.
4. כותבים את המסמך. ממלאים ב-`spec/prd.md` את הסעיפים של התבנית לפי הסדר שלה. סעיף שמסומן "תלוי במצב" ממלאים רק כשהתנאי שלו מתקיים, ואחרת מוחקים אותו:
   - הבעיה במשפט אחד, ולמה עכשיו, מתוך התשובה הראשונה של הסטודנט.
   - מי משתמש, ובאילו תפקידים.
   - המטרות ומה לא מטרה.
   - מה ייחשב כישלון גם אם הכל עובד (`<!-- prd:anti-goals -->`). Claude מציע שתי אפשרויות, והסטודנט בוחר אחת או כותב משלו, במשפט אחד או שניים.
   - מדדי הצלחה למוצר כולו, שאפשר למדוד אחרי ההשקה.
   - היכולות. לכל יכולת כותבים משפט אחד שאומר איך נדע שהיא עובדת, בניסוח של קריטריון קבלה: מי עושה מה, באיזה תנאי ומה רואים בסוף.
   - מקרי קצה ומקרי כשל, ולכל אחד הבדיקה שמכסה אותו.
   - סוגי המידע שהמערכת שומרת.
   - מטריצת הרשאות, עם התפקידים בשורות וסוגי המידע בעמודות. בכל תא כתוב אם מותר ליצור, לקרוא, לעדכן או למחוק, ואם רק את שלו או את של כולם. אף תא לא נשאר ריק, ומה שאסור כתוב בו "אסור".
   - מטריצת אוטונומיה, כשיש אוטומציות. לכל אוטומציה כותבים מה מפעיל אותה, באיזו רמה היא רצה, מי מאשר, מה קורה כשהיא נכשלת ומה התקרה שלה. החלטה שאפשר לכתוב ככלל בקוד לא משאירים למודל.
   - המסלול, המגבלות של התוכניות שנבחרו ושורה עם העלות החודשית.
   - ההחלטות, ולכל אחת האפשרויות שנשקלו והנימוק.
   - מה הבונה מחליט לבד.
   - הנחות, כשיש.
   - שאלות פתוחות. כשאין, כותבים "אין".
   - מתי העבודה גמורה, ברשימה שהסוכן יכול לבדוק בעצמו.
   - מה נדחה ל"לא עכשיו". כל מה שנדחה רושמים גם ב-`bp map later add "<מה>" --stage 4`.
5. עושים על המסמך את שש הבדיקות, כלומר עוברים עליו ושואלים שש שאלות:
   - האם יש דרישה שאי אפשר לבדוק?
   - האם יש פעולה שיוצאת החוצה מהמערכת בלי אישור?
   - האם יש נתון שלא ברור איפה הוא נשמר ומי קורא אותו?
   - האם יש תוכן שלא ברור מי שולט בו?
   - האם יש תקלה שלא הוגדר מה קורה בה?
   - האם יש החלטה שהשארנו למודל, למרות שאפשר לכתוב אותה ככלל בקוד?
   כל ממצא נסגר באחת משתי דרכים: Claude מתקן ורושם הכרעה (`bp ruling add ... stage=4`), או שהשאלה עוברת לסטודנט. את הממצאים כותבים בקובץ נפרד, `spec/prd-review.md`, כי הם חלק מהסקירה ולא דרישה של המוצר.
6. מראים לסטודנט את המסמך ומתקנים, עד שהוא מאשר מה נכנס ומה נדחה.

## מה חייב להיות נכון בסוף (ההוכחה)

- הבדיקה `node scripts/blueprint-check.mjs` לא מחזירה אזהרה על הסעיף "מה ייחשב כישלון", ולא על הסעיפים מדדי הצלחה, מקרי קצה, שאלות פתוחות ומתי העבודה גמורה.
- לכל יכולת ב-`spec/prd.md` יש משפט הוכחה, ובמטריצת ההרשאות אין תא ריק.
- הפקודה `bp state get track` מחזירה מסלול, וב-`.blueprint/changes.json` יש רשומה מסוג `track`.
- לכל נקודת החלטה שנפתחה יש בחירה רשומה.
- כל מה שנדחה נמצא ברשימה `later` שבקובץ `.blueprint/map.json`.

## מה נשאר בתיקייה

- `spec/prd.md`
- הממצאים של שש הבדיקות, בקובץ `spec/prd-review.md`
- יומן השינויים `.blueprint/changes.json`, עם הבחירות

## סגירה

1. מריצים את בדיקות ההוכחה ושומרים את הפלט שהן החזירו בפועל.
2. מציגים לסטודנט את ההכרעות של השלב שעוד לא ראה, עם `bp ruling list --unreported --stage 4`, ואחר כך מריצים `bp ruling report --stage 4`.
3. סוגרים את השלב עם `bp stage done 4 --status <done|done_with_concerns|blocked|needs_context> --note "<מה פתוח>" --proof "<הפלט>"`.
4. עושים commit בענף `stage-04` עם הודעה בעברית, פותחים PR וממזגים אחרי שהבדיקה עוברת.
5. כותבים את `.blueprint/last-session.md`.
6. אומרים לסטודנט במשפט אחד, בלי לייפות, איך השלב נסגר. אחר כך אומרים בשתי שורות שהשלב הבא הוא מפת המסכים, ושפותחים אותו בשיחה חדשה עם `/blueprint`.
