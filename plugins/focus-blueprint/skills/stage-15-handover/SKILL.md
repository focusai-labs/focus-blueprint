# שלב 15: מסירה

בכל מקום שכתוב `bp`, מריצים `node "${CLAUDE_PLUGIN_ROOT}/scripts/bp.mjs"`.

## למה השלב הזה קיים

כשהמסירה היא רק קובץ ששולחים, הלקוח מתקשר בכל פעם שמשהו לא ברור לו. במסירה טובה, מי שיפעיל את המערכת מבצע לבד את המשימות הנפוצות, ובכל מקום שבו הוא נתקע מתקנים את המדריך או את המערכת.

## מה קוראים לפני שמתחילים

- בקובץ המצב `.blueprint/state.json` בודקים שהשלב הנוכחי הוא 15, וקוראים את ההקשר בשדה `context` ואת השדה `where`, שאומר איפה כל דבר נמצא.
- התבניות של המסירה בתיקייה `${CLAUDE_PLUGIN_ROOT}/templates/docs`, לפי ההקשר. ללקוח יש שלוש: `handover-client.md` (מדריך הפעלה), `handover-client-developer.md` (מסמך למפתח) ו-`handover-client-accounts.md` (רשימת החשבונות). בארגון התבנית היא `handover-org.md`, ולעצמכם `handover-self.md`.

## מה עושים

1. מריצים `bp stage start 15`. מעבירים לסטודנט, מילה במילה, את הפתיחה שהפקודה הדפיסה.
2. כותבים מהתבניות את מסמכי המסירה לתיקייה `docs`. המדריך בנוי ממשימות, וליד כל צעד כתוב מה אמור לקרות. ברשימת החשבונות כתוב על שם מי כל חשבון רשום, מי משלם עליו ומתי הוא מתחדש, בלי אף סיסמה או מפתח. סעיף שמסומן "תלוי במצב" ממלאים רק כשהתנאי שלו מתקיים, ואחרת מוחקים אותו.
3. בוחרים עם הסטודנט שלוש משימות שמי שיפעיל את המערכת עושה לבד, למשל להוסיף לקוח, לשנות נוסח של תזכורת ולבדוק מי לא שלח החודש.
4. מי שיפעיל את המערכת מבצע אותן לפי המדריך, בלי עזרה, והסטודנט מספר מה קרה. ב-`docs/handover-test.md` כותבים לכל משימה אם היא הצליחה, ואיפה הוא נתקע.
5. מתקנים את המדריך או את המערכת, ובודקים שוב את מה שנתקע.
6. שומרים בפרופיל האישי את הפרויקט, עם `bp profile set projects='[…]'`, ואת מערכת העיצוב, עם `bp profile set designSystems='[…]'`, כדי שאפשר יהיה להשתמש בהם שוב.
7. כשמבקשים דוח חודשי, מפיקים את `docs/report-<yyyy-mm>.md` מהתבנית `${CLAUDE_PLUGIN_ROOT}/templates/docs/report-<client|org|self>.md`. את העלות בודקים בחשבונות של הספקים, ולא לפי מה שהמודל דיווח. בודקים גם את המשפט מה-PRD שאומר איך נדע שהמערכת עובדת.

## מה חייב להיות נכון בסוף (ההוכחה)

- בקובץ `docs/handover-test.md` יש שלוש משימות, ולכל אחת כתובה התוצאה.
- במסמכי המסירה אין אף סיסמה, מפתח או טוקן.
- ברשימת החשבונות יש לכל חשבון בעלים, מי משלם ומועד חידוש.
- כל משימה שנתקעה תוקנה ונבדקה שוב.

## מה נשאר בתיקייה

- מסמכי המסירה, וקובץ הבדיקה `docs/handover-test.md`
- הפרויקט ומערכת העיצוב בפרופיל האישי

## סגירה

1. מריצים את בדיקות ההוכחה ושומרים את הפלט שהן החזירו בפועל.
2. מציגים לסטודנט את ההכרעות של השלב שעוד לא ראה, עם `bp ruling list --unreported --stage 15`, ואחר כך מריצים `bp ruling report --stage 15`.
3. סוגרים את השלב עם `bp stage done 15 --status <done|done_with_concerns|blocked|needs_context> --note "<מה פתוח>" --proof "<הפלט>"`.
4. עושים commit בענף `stage-15` עם הודעה בעברית, פותחים PR וממזגים אחרי שהבדיקה עוברת.
5. כותבים את `.blueprint/last-session.md`.
6. אומרים לסטודנט במשפט אחד, בלי לייפות, איך השלב נסגר. אחר כך מעבירים לסטודנט, מילה במילה, את השורה על השלב הבא שהפקודה `bp stage done` הדפיסה. מעכשיו כל שינוי במערכת עובר דרך `/blueprint`.
