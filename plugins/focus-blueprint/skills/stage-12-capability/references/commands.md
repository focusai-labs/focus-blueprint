# הפקודות של שלב 12, צעד אחרי צעד

בכל מקום שכתוב `bp`, מריצים `node "${CLAUDE_PLUGIN_ROOT}/scripts/bp.mjs"`.

## התקציר

- הפקודה `bp brief <id>` יוצרת את `evals/briefs/<id>.md` מהמפה, עם המסכים, הטבלאות, ההרשאות, האוטומציות ונתיב הבדיקה.
- בטבלת הערכים, כל שורה היא ערך מדויק ומקור קיים, למשל `| העלאה הושלמה | mockup/upload.html |`. הבדיקה של המפה מוודאת שהמקור קיים.

## הבדיקה והראיות

- הפקודה `bp eval new <id>` יוצרת את `evals/<id>.md`, עם המשפט של מה הבדיקה תופסת וחמשת מצבי הכשל.
- כשהבדיקה רצה בדפדפן דרך ה-MCP של Playwright ולא כסקריפט, שומרים את הדוח לקובץ, ומריצים `bp evidence red <id> --report <file> --result fail`, ואחר כך את אותו הדבר עם `green` ו-`pass`.
- הכלי מסרב לראיה אדומה של בדיקה שעברה, ולראיה ירוקה בלי אדומה לפניה. ריצה שלא רצה בכלל, למשל פקודה שלא נמצאה, לא נרשמת.

## הסקירה

- הסקירה נכתבת לקובץ `evals/reviews/<id>.md`, עם שני פסקי דין: עמידה באפיון, ואיכות. לכל ממצא יש קובץ ושורה.
- רק אחרי ששניהם "עבר", מריצים `bp review record <id> --spec pass --quality pass --path evals/reviews/<id>.md`.

## בקשת מיזוג, PR, ומיזוג

- לכל יכולת יש PR משלו. ב-PR רצות הבדיקות: ה-build, בדיקות הקבלה ובדיקת המפה.
- במאגר פרטי בחשבון החינמי, GitHub לא חוסם בעצמו מיזוג של PR אדום. לכן הכלי חוסם מיזוג מקומי ל-main, ו-Claude לא ממזג PR אדום.

## כשמשהו שבור כבר עלה

- ב-Vercel יש חזרה מיידית לגרסה הקודמת. בחשבון החינמי אפשר לחזור רק לגרסה שלפני האחרונה.
- אחרי חזרה, Vercel מפסיקה להעלות לאוויר את מה שנכנס ל-main, עד שמבטלים את החזרה. המקור: https://vercel.com/docs/instant-rollback
- את התיקון עושים בענף, דרך PR ובדיקה ירוקה, ורק אז מבטלים את החזרה.
