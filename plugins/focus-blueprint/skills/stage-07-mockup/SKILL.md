# שלב 07: בניית ה-mockup

בכל מקום שכתוב `bp`, מריצים `node "${CLAUDE_PLUGIN_ROOT}/scripts/bp.mjs"`.

## למה השלב הזה קיים

היום בונים מסך בכמה דקות, ולכן ה-mockup הוא חלק מהאפיון ולא מהבנייה. כשמסתכלים על מסך אמיתי, אפשר לשאול שאלות שנשארות פתוחות כשיש רק תיאור כתוב: מה קורה כשלוחצים, מי רואה מה ומה קורה כשמשהו נכשל. מסד הנתונים עוד לא קיים, ולכן תיקון בעקבות תשובה לוקח דקה ולא יום.

## מה קוראים לפני שמתחילים

- בקובץ המצב `.blueprint/state.json` בודקים שהשלב הנוכחי הוא 7. אם לא, מפנים את הסטודנט ל-`/blueprint`.
- רשימת המסכים במפה `.blueprint/map.json`, והמסמכים `spec/screens-map.md`, `spec/journeys.md` ו-`design/design-system.md`.
- העקרונות שמסומנים לשלב 7 בקובץ `${CLAUDE_PLUGIN_ROOT}/data/ux/principles.json`. קוראים אותם לפני שבונים את המסך הראשון.
- הכללים לבניית מסך, בקובץ `${CLAUDE_PLUGIN_ROOT}/skills/stage-07-mockup/references/mockup-rules.md`.

## מה עושים

1. מריצים `bp stage start 7`.
2. כותבים קובץ אחד של נתוני דמה, `mockup/mock-data.js`, עם נתונים שנראים אמיתיים אבל בלי פרטים של אנשים אמיתיים. כותבים גם קובץ עיצוב אחד, `mockup/mock.css`, שטוען את `design/tokens.css`.
3. בונים כל מסך שבמפה, בקובץ שרשום לו, לפי הכללים שבקובץ הכללים: כיוון מימין לשמאל, פעולה ראשית אחת, אישור לפני מחיקה, דרך חזרה לדף הבית, תווית לכל שדה, הודעת שגיאה ליד השדה, מצב טעינה ושמירה של טיוטות.
4. כשמסך מוכן, מקשרים אליו כל צעד בתהליכים שאדם עושה בו, עם `bp process step set <process> <step> --json '{"screen":"mockup/<id>.html"}'`. צעד של אוטומציה, של שרת, של AI או של שירות חיצוני נשאר בלי מסך, וגם צעד שאדם עושה מחוץ למערכת, כמו שיחת טלפון. כשכל המסכים מוכנים, מריצים `bp render`, כדי שהחותמת של ה-PRD תתאים למפה.
5. אם הוחלט שיהיה תשלום, משאירים לו מקום במסכים, עם כפתור שמסומן כדמה.
6. מעלים את התיקייה `mockup` ל-Vercel ומקבלים קישור, לפי השלב של ה-mockup במסלול, בקבצים שבתיקייה `${CLAUDE_PLUGIN_ROOT}/data/tracks` (השלב הוא הצעד של המסלול ששלב 7 רשום בו). כשבמסלול אין צעד כזה, עושים לפי ההוראות כאן: HTML פשוט עם קובץ אחד של נתוני דמה, שעולה ל-Vercel כפרויקט שמחובר ל-repo, בלי שום סוד בקבצים. לפני הפקודה קוראים את התיעוד דרך `/focus-blueprint:docs-verify`. רושמים את הקישור עם `bp state set where.mockupUrl=<url>`.
7. פותחים את הסבב השלישי עם `node "${CLAUDE_PLUGIN_ROOT}/ui/serve.mjs" --page questionnaire --round c`. בסבב הזה הסטודנט עונה רק על שאלות שהתשובה עליהן נמצאת אצלו: מי רואה כל מסך, מה יוצא ממנו ולמי, ואיזו פעולה אי אפשר לבטל. המסך שהשאלה עוסקת בו מוצג ליד השאלה. כשתשובה משנה מסך, מתקנים אותו מיד. כשתשובה משנה את האפיון, מכניסים אותה ל-PRD עם סימון המקור שלה ולמסמך ההחלטות, ומה שנוגע במפה משנים רק דרך `bp` ואחר כך מריצים `bp render`.
8. את שאר השאלות של הסבב, אלה שמסומנות `"by": "claude"` בקובץ `${CLAUDE_PLUGIN_ROOT}/data/questions/round-c.json`, Claude בודק בעצמו בכל מסך עם Playwright: מה קורה בלחיצה על הפעולה הראשית ובלחיצה כפולה, מה רואים כשמשהו נכשל, לפני שיש נתונים ובזמן המתנה, איך חוזרים לדף הבית ומה קורה למה שכבר הוקלד, ואיך המסך עובד בטלפון ביד אחת. את התשובות הוא רושם עם `bp answer set c <id> --value "<מה נבדק ומה נמצא>"`, ומראה לסטודנט סיכום קצר. מה שנכשל מתקנים לפני שממשיכים.
9. מריצים את `/focus-blueprint:ux-review` על כל המסכים. מתקנים כל עיקרון ברמה `must` שנכשל, ומריצים שוב עד שהכל עובר. עיקרון ברמה `should` שלא מתקנים עכשיו נכנס לרשימת "אחר כך", עם הסיבה.

## מה חייב להיות נכון בסוף (ההוכחה)

- כל קובץ מסך שרשום במפה קיים בתיקייה `mockup`.
- בקובץ `spec/ux-review.md` אין אף עיקרון `must` שנכשל.
- הפקודה `bp state get where.mockupUrl` מחזירה קישור שנפתח.
- הבדיקה `node scripts/blueprint-check.mjs` לא מחזירה שגיאה או אזהרה בכללים 1 ו-2, ועוברת את כלל 18, שבודק שכל צעד מפנה למסך שקיים במפה.
- לכל צעד של תפקיד שקורה בתוך המערכת יש מסך. סקריפט קצר עם `node -e` מדפיס מהמפה את הצעדים של תפקידים שאין להם מסך, ועל כל אחד מהם כותבים בסגירה למה הוא קורה מחוץ למערכת.

## מה נשאר בתיקייה

- כל המסכים בתיקייה `mockup`, יחד עם `mock-data.js` ו-`mock.css`
- דוח הסקירה `spec/ux-review.md`, ותשובות הסבב השלישי במסמך ההחלטות
- המפה `.blueprint/map.json`, שבה לכל צעד של אדם יש את המסך שלו

## סגירה

1. מריצים את בדיקות ההוכחה ושומרים את הפלט שהן החזירו בפועל.
2. מציגים לסטודנט את ההכרעות של השלב שעוד לא ראה, עם `bp ruling list --unreported --stage 7`, ואחר כך מריצים `bp ruling report --stage 7`.
3. סוגרים את השלב עם `bp stage done 7 --status <done|done_with_concerns|blocked|needs_context> --note "<מה פתוח>" --proof "<הפלט>"`. כשנדחה עיקרון `should`, הסטטוס הוא `done_with_concerns`.
4. עושים commit בענף `stage-07` עם הודעה בעברית, פותחים PR וממזגים אחרי שהבדיקה עוברת.
5. כותבים את `.blueprint/last-session.md`.
6. אומרים לסטודנט במשפט אחד, בלי לייפות, איך השלב נסגר, ונותנים לו את הקישור ל-mockup. אחר כך אומרים בשתי שורות שהשלב הבא הוא הצגה לאדם אמיתי, ושפותחים אותו בשיחה חדשה עם `/blueprint`.
