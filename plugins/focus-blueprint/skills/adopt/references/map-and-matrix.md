# המפה ומטריצת ההרשאות בפרויקט קיים

בכל מקום שכתוב `bp`, מריצים `node "${CLAUDE_PLUGIN_ROOT}/scripts/bp.mjs"`.

הצעד הזה מתחיל אחרי העצירה הראשונה, כשהסטודנט כבר אישר את הסקירה. מכאן כל מה שנמצא בסקירה נרשם כנתונים במפה, כי ממנה הבדיקות, השומרים והמסמכים יודעים מה קיים.

## הכלי בפרויקט

1. מריצים את `bp init --name "<שם הפרויקט>"`, שלא דורסת קבצים קיימים. הפקודה מוסיפה את כללי העבודה ל-`AGENTS.md`, מעתיקה את הבדיקה ל-`scripts/blueprint-check.mjs` ומתקינה את ה-hook של git לפני commit. מהרגע הזה commit עובר רק כשהבדיקה עוברת, ולכן ה-commit הראשון בענף `adopt` בא אחרי שהתיקונים של צעד 3 סוגרים את השגיאות על המיגרציות ועל הסודות.
2. כשבמערכת כבר יש משתמשים אמיתיים, מריצים מיד `bp state set live=true`. מאז השומרים לא מאפשרים לדחוף שינוי ישר לפרודקשן, ומיגרציה חדשה רק מוסיפה דברים לסכמה.
3. רושמים את המסלול עם `bp state set track=<supabase-app|n8n-engine|static>`, ואת תוצאות החיבורים עם `bp connections set`.
4. מחילים את השינויים מ-`spec/adopt-setup.md` שהסטודנט אישר, ומראים לו את `git diff` של כל קובץ. כשיש בפרויקט `CLAUDE.md`, השורה `@AGENTS.md` נכנסת אליו בכל מקרה, אחרי שהסטודנט ראה אותה, כי בלעדיה Claude Code לא קורא את כללי הכלי.

## המפה

1. מסדרים את המיגרציות לפי `migrations.md`, ורק אחר כך רושמים טבלאות, כי כל טבלה מפנה לקובץ שיוצר אותה.
2. רושמים את המסכים, הטבלאות, האוטומציות והיכולות עם `bp map add`.
3. כל שירות נרשם עם `bp service add <id> --json '<obj>'`, עם מה הוא עושה, על שם מי החשבון ומי משלם, ועם השמות של הסודות ושל המשתנים הציבוריים שלו. ל-Supabase רושמים גם את `ref` של הפרודקשן, את `prodBranch` ואת `devTarget`, כי מהם השומרים יודעים מה נחשב פרודקשן.
4. יכולת שכבר עובדת מסמנים עם `bp map set capability <id> status=real --baseline`. הסימון אומר שהיא לא נבנתה דרך התהליך, והבדיקה מזכירה את זה באזהרה. מיד אחריו יוצרים לה קובץ בדיקה עם `bp eval new <id>`, כי הבדיקה דורשת קובץ בדיקה לכל יכולת אמיתית.
5. על האתר החי מריצים את סריקת המלאי, `${CLAUDE_PLUGIN_ROOT}/scripts/inventory.browser.js`, ואת `/focus-blueprint:ux-review`. התוצאה נשמרת ב-`spec/ux-review.md` כקו בסיס. בכניסה לפרויקט קיים לא מתקנים בשלב הזה מסכים. כל `must` שנכשל נרשם עם `bp map later add "<העיקרון, המסך והסיבה>"`, ומטפלים בו אחרי הכניסה, כשינוי רגיל.

## מטריצת ההרשאות

1. כל תפקיד נרשם עם `bp role add <id> --name "<השם>" --kind <anon|user|staff|admin|service>`.
2. כל טבלה, תצוגה, פונקציה ותיקיית קבצים נרשמת עם `bp access set <object> --json '<obj>'`, עם מה מותר לכל תפקיד, על אילו שורות, ואילו עמודות רגישות.
3. המטריצה מתארת את מה שהמערכת צריכה, לפי הקוד ולפי מה שהסטודנט אומר על השימוש בה. מה שהמסד מתיר היום לא קובע אותה.
4. ברירת המחדל היא שהכל חסום. על תא שלא ברור שואלים את הסטודנט, ואף פעם לא מכריעים לטובת יותר גישה.
5. בדוח הסקירה, בחלק של המטריצה, מוסיפים את הסימונים `<!-- gen:roles -->` ו-`<!-- gen:permissions -->`, כל אחד עם סימון הסגירה שלו, ומריצים `bp render --file spec/adopt-review.md`. הכלי כותב את הטבלאות מהמפה.
6. ליד המטריצה כותבים את הפער: לכל אובייקט, מה המסד מתיר היום ומה המטריצה קובעת. כל פער כזה יקבל תיקון בצעד 3.

כאן עוצרים בפעם השנייה. עוברים עם הסטודנט על המטריצה תא אחרי תא, ועל רשימת הפערים. כל תיקון שלו נרשם עם `bp access set`, ואחריו מריצים שוב את `bp render`.
