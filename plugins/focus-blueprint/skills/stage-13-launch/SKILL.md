# שלב 13: רשימת השקה

בכל מקום שכתוב `bp`, מריצים `node "${CLAUDE_PLUGIN_ROOT}/scripts/bp.mjs"`.

## למה השלב הזה קיים

בהשקה טובה מגלים את הבעיות לפני שהלקוח מגלה אותן. לכן שוברים את המערכת בכוונה, לפני שמישהו ישבור אותה בטעות. בודקים שלקוח אחד לא רואה נתונים של לקוח אחר, שאין סוד שמגיע לדפדפן, שיש התראה כשמשהו נופל ושאפשר לשחזר את הנתונים. כל שורה ברשימה נסגרת עם ראיה, ולא עם "נראה בסדר".

## מה קוראים לפני שמתחילים

- בקובץ המצב `.blueprint/state.json` בודקים שהשלב הנוכחי הוא 13, וקוראים את המסלול.
- הצעדים של המסלול לשלב 13, בקובץ `${CLAUDE_PLUGIN_ROOT}/data/tracks/<track>.json`. לצעד שתלוי בצורך יש שדה `when`, לצעד בתשלום יש שדה `paid`, ולמה שעושים בתוכנית החינמית יש שדה `onFree`.
- מפת התהליך ב-`.blueprint/map.json`: הצעדים שרצים בלי אדם, מסוג `system` או `ai`, עם השדה `onFailure` שלהם, והטיימרים.
- הממצאים מבדיקת השמישות בקובץ `spec/usability-test.md`, ודוח הסקירה `spec/ux-review.md`.

## מה עושים

1. מריצים `bp stage start 13`. מעבירים לסטודנט, מילה במילה, את הפתיחה שהפקודה הדפיסה.
2. כותבים ב-`docs/critical-points.md` מה שוברים בכוונה ומה צריך לקרות כשזה נשבר. למשל משתמש שני שמנסה לקרוא נתונים של משתמש אחר, שליחה כפולה, רשת שנופלת באמצע ומפתח שחסר.
3. עוברים על רשימת ההשקה בקובץ `docs/launch-checklist.md`, וכותבים ליד כל שורה את הראיה. שורה שהתנאי שלה לא מתקיים בפרויקט נשארת ברשימה עם המילים "לא רלוונטי" והסיבה. את הכוונה, הקישור לתיעוד ושורת הבטיחות של כל שורה קוראים בצעד המתאים במסלול, ולפני כל פקודה של ספק עוברים דרך `/focus-blueprint:docs-verify`.

   | הנושא | מתי | מה מוכיח שזה עובד |
   |---|---|---|
   | בידוד נתונים | תמיד | בבדיקה חיה, משתמש שני לא רואה אף שורה של המשתמש הראשון |
   | אבטחה | תמיד | ה-advisors מסוג security ומסוג performance לא מוצאים בעיות, עם `supabase db advisors --remote --type all` או עם `get_advisors` |
   | סודות | תמיד | אף מפתח סודי לא נמצא בקוד שמגיע לדפדפן, ומשתני הסביבה מוגדרים ב-Vercel |
   | דומיין | כשיש דומיין | הדומיין מחובר לפי הצעדים של המסלול |
   | התראות | לכל צעד שרץ בלי אדם במפת התהליך | מכשילים את הצעד בכוונה, וההתראה שבשדה `onFailure` שלו מגיעה. מצטטים אותה |
   | טיימרים | לכל טיימר במפת התהליך | בדיקה או משימה מתוזמנת מראות שמה שאמור לקרות כשהזמן נגמר באמת קרה |
   | חוויית משתמש | תמיד | סקירת UX עם `/focus-blueprint:ux-review` רצה על כל המערכת החיה, וכל ממצא מבדיקת השמישות נסגר |
   | גיבוי | כשיש נתונים של משתמשים אמיתיים | תרגיל שחזור אחד לפרויקט חדש מוצא שורה ידועה, וכתוב כמה זמן הוא לקח |
   | שחזור לנקודת זמן | כשאסור לאבד אפילו יום של נתונים | תרגיל שחזור לנקודת זמן מוצא שורה שנכתבה רגע לפניה |
   | סיסמאות שדלפו | כשנכנסים עם סיסמה | הרשמה עם סיסמה ידועה שדלפה נדחית |
   | שרת מיילים | כשנרשמים או מקבלים קישור במייל | משתמש מחוץ לצוות מקבל את המייל מהשולח של העסק |
   | חזרה לגרסה קודמת | כשהמערכת באוויר | תרגיל חזרה ב-Vercel לגרסה קודמת ובחזרה, עם הכתובות ועם הזמן |
   | סביבות תצוגה | כשלקוח רואה תצוגות | כתובת תצוגה שנפתחת בחלון פרטי מבקשת סיסמה או התחברות |
   | גרסאות | תמיד | קובץ הנעילה נמצא ב-Git, והתקנה נקייה ממנו בונה את האפליקציה |

4. כל יכולת ברשימה מתחילה מהצורך שבעמודה "מתי". כשהיכולת דורשת תוכנית בתשלום, כמו גיבוי יומי ושחזור לנקודת זמן ב-Supabase או חזרה לכל גרסה והגנה בסיסמה ב-Vercel, ממליצים על התוכנית הזאת, ואת המחיר קוראים בתיעוד עם התאריך. מעבר לתוכנית בתשלום עולה כסף, ולכן שואלים את הסטודנט לפני. כשהסטודנט או הלקוח נשארים בתוכנית החינמית, מוסיפים את הבקרות שבשדה `onFree` של הצעד, רושמים את הפער ואת הסיכון שלו עם `bp ruling add`, וכותבים אותו גם ליד השורה ברשימה. כל פעולה שהסטודנט עושה בלוח בקרה, Claude מוביל פעולה אחרי פעולה, כמו שכתוב ב-`${CLAUDE_PLUGIN_ROOT}/skills/stage-01-connect/references/supabase-connect.md`.
5. שוברים בכוונה כל נקודה במפת הנקודות הקריטיות, ובודקים שקרה מה שצריך לקרות.
6. במסלול של אפליקציה עם משתמשים מכינים את יעד הפיתוח לשינויים שאחרי ההשקה, לפי הצעד `sb-dev-target`:
   - בתוכנית Pro, ענף התצוגה של כל PR הוא יעד הפיתוח, והבדיקה Supabase Preview חייבת לעבור. כשצריך לבדוק לפני שיש PR, הסטודנט פותח ענף קבוע אחד, ו-Claude רושם את השם שלו.
   - בתוכנית החינמית הסטודנט פותח פרויקט פיתוח חדש, ומעלה אליו בעצמו את כל המיגרציות עם `supabase db push --remote=<ref של הפיתוח>`, בחלון טרמינל רגיל, כי הפקודה שואלת את סיסמת המסד של הפרויקט הזה. רושמים את הפער לפי השדה `onFree` של הצעד.
   - רושמים במפה את היעד עם `bp service set supabase --json '{"devTarget":"<ref של הפיתוח או שם הענף>"}'`, ומכוונים את סביבות התצוגה של Vercel אל יעד הפיתוח, כי אחרת הן קוראות וכותבות בפרודקשן.
   - חיבור ה-MCP של הפרודקשן נשאר מוגבל לפרויקט אחד ולקריאה בלבד.
7. במסלול של אפליקציה עם משתמשים מוסיפים את הבדיקה השבועית של ה-advisors, לפי הצעד `sb-weekly-advisors`. כיוון ש-GitHub מריץ תזמון רק מהענף הראשי, היא נכנסת ב-PR משלה:
   - בענף נפרד Claude מעתיק את `${CLAUDE_PLUGIN_ROOT}/templates/github/supabase-advisors.yml` ל-`.github/workflows/supabase-advisors.yml`, ומריץ `gh variable set SUPABASE_PROJECT_REF --body <ref של הפרודקשן>`.
   - הסטודנט יוצר בלוח הבקרה של Supabase טוקן שמוגבל לפרויקט הפרודקשן ולהרשאה Advisors לקריאה בלבד, ו-Claude מוביל אותו פעולה אחרי פעולה. אחר כך הסטודנט מריץ בעצמו `gh secret set SUPABASE_ACCESS_TOKEN` ומדביק את הטוקן כשהפקודה מבקשת, כדי שהטוקן לא יעבור בשיחה.
   - אחרי המיזוג Claude מריץ `gh workflow run supabase-advisors.yml`, ובודק עם `gh run list --workflow supabase-advisors.yml` שהריצה הסתיימה. מייל על ריצה שנכשלה מגיע למי שהוסיף את הקובץ ל-GitHub, ולכן בפרויקט של לקוח בודקים שזה האדם הנכון.
8. כשיש ראיה לכל שורה, מסמנים שהמערכת באוויר עם `bp state set live=true`. מהרגע הזה מיגרציה רק מוסיפה דברים לסכמה, וה-hook חוסם מחיקה. גם דחיפה של מיגרציה לפרודקשן נחסמת, כי לשם היא מגיעה רק במיזוג.

## מה חייב להיות נכון בסוף (ההוכחה)

- בקובץ `docs/launch-checklist.md` יש ראיה לכל שורה, או "לא רלוונטי" עם הסיבה.
- כל נקודה בקובץ `docs/critical-points.md` נשברה בכוונה, והתוצאה כתובה.
- לכל פער של תוכנית חינמית יש הכרעה רשומה עם הסיכון שלו.
- במסלול של אפליקציה עם משתמשים, הריצה הידנית של `supabase-advisors` הסתיימה, והשירות `supabase` במפה מחזיק את `ref`, את `prodBranch` ואת יעד הפיתוח.
- הסגירה עוברת דרך `/focus-blueprint:verify`, והפלט שלה מצוטט.

## מה נשאר בתיקייה

- הקבצים `docs/launch-checklist.md` ו-`docs/critical-points.md`
- במסלול של אפליקציה עם משתמשים, הקובץ `.github/workflows/supabase-advisors.yml`
- הדגל `live` בקובץ המצב

## סגירה

1. מריצים את `/focus-blueprint:verify` ואת בדיקות ההוכחה, ושומרים את הפלט שהם החזירו בפועל.
2. מציגים לסטודנט את ההכרעות של השלב שעוד לא ראה, עם `bp ruling list --unreported --stage 13`, ואחר כך מריצים `bp ruling report --stage 13`.
3. סוגרים את השלב עם `bp stage done 13 --status <done|done_with_concerns|blocked|needs_context> --note "<מה פתוח>" --proof "<הפלט>"`. כששורה ברשימה נסגרה למרות פער ידוע, הסטטוס הוא `done_with_concerns`, וכותבים את הפער בהערה.
4. עושים commit בענף `stage-13` עם הודעה בעברית, פותחים PR וממזגים אחרי שהבדיקה עוברת.
5. כותבים את `.blueprint/last-session.md`.
6. אומרים לסטודנט במשפט אחד, בלי לייפות, איך השלב נסגר. אחר כך אומרים בשתי שורות שהשלב הבא הוא הסליקה, אם הוחלט שיהיה תשלום, ואם לא, המסירה. פותחים אותו בשיחה חדשה עם `/blueprint`.
